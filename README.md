# Wallet Service

Асинхронный REST API для операций по кошелькам пользователей. FastAPI, PostgreSQL, SQLAlchemy 2.0 в асинхронном режиме, Alembic. Вся система поднимается одной командой через docker compose. Ключевое свойство сервиса: параллельные операции над одним и тем же кошельком обрабатываются корректно, без потерянных обновлений и без возможности увести баланс в минус.

## Запуск

```bash
cp .env.example .env
docker compose up --build
```

Поднимаются три сервиса: база, разовый прогон миграций и API. Приложение стартует только после того, как база прошла healthcheck и миграции завершились успешно, поэтому под трафик никогда не попадает наполовину применённая схема. API доступен на http://localhost:8000, Swagger на http://localhost:8000/docs.

Тесты запускаются отдельным профилем, в контейнере, против настоящего PostgreSQL:

```bash
docker compose --profile test run --rm tests
```

То же самое есть в Makefile: `make up`, `make test`, `make lint`, `make clean`.

## Что реализовано

Три эндпоинта из задания: создание кошелька, чтение баланса, изменение баланса. Создания в исходном ТЗ нет, но без него кошелёк нечем завести, поэтому оно добавлено. Сверх задания сделаны три вещи, каждая из которых объясняется ниже: журнал операций, идемпотентность по необязательному заголовку и health-эндпоинты для оркестратора.

Создание кошелька, тело запроса необязательно и по умолчанию даёт нулевой баланс:

```http
POST /api/v1/wallets
Content-Type: application/json

{"initial_balance": "1000.00"}
```

Ответ `201 Created` с телом `{"id": "...", "balance": "1000.00"}`.

Чтение баланса:

```http
GET /api/v1/wallets/{WALLET_UUID}
```

Ответ `200 OK` с телом `{"id": "...", "balance": "1000.00"}`.

Изменение баланса, заголовок `Idempotency-Key` необязателен:

```http
POST /api/v1/wallets/{WALLET_UUID}/operation
Content-Type: application/json
Idempotency-Key: order-4711

{"operation_type": "DEPOSIT", "amount": 1000}
```

Ответ `200 OK` с телом `{"wallet_id": "...", "operation_id": "...", "operation_type": "DEPOSIT", "amount": "1000.00", "balance": "2000.00", "replayed": false}`.

Коды ответов распределены так. `200` означает, что операция применена или распознана как повтор. `201` возвращается при создании кошелька. `404` означает, что кошелька с таким UUID не существует. `409` отдаётся в двух случаях: недостаточно средств для списания, либо ключ идемпотентности переиспользован с другим телом запроса. `422` означает невалидный запрос: сумма меньше или равна нулю, больше двух знаков после запятой, неизвестный `operation_type`, битый UUID в пути, лишние поля в теле. `503` означает, что база недоступна или транзакция не прошла после всех повторов.

Любая ошибка, независимо от кода, приходит в одном формате:

```json
{
  "code": "insufficient_funds",
  "message": "Wallet ... has insufficient funds for a withdrawal of 500.00",
  "request_id": "0f6c...",
  "details": null
}
```

Поле `code` стабильно и предназначено для машинной обработки, `message` для человека, `request_id` совпадает с заголовком ответа `X-Request-ID` и с полем в логах, `details` заполняется только для ошибок валидации и перечисляет проблемные поля.

Есть два health-эндпоинта. `GET /health/live` сообщает, что процесс жив, и намеренно не трогает базу: кратковременный сбой БД не должен приводить к тому, что оркестратор убьёт здоровый процесс. `GET /health/ready` сообщает, что сервис готов принимать трафик, то есть база отвечает на запрос.

## Конкурентность

Это основная часть задачи, поэтому подробно. Изменение баланса выполняется одним атомарным SQL-оператором:

```sql
UPDATE wallets
   SET balance = balance + :delta
 WHERE id = :wallet_id
   AND balance + :delta >= 0
RETURNING balance;
```

Такая форма выбрана по четырём причинам. Первая: здесь нет окна read-modify-write. Классическая ошибка в этой задаче — прочитать баланс в Python, посчитать новое значение и записать его обратно; между чтением и записью успевает вклиниться другая транзакция, и одно из списаний теряется. В этом решении чтения на стороне приложения нет вообще, текущее и новое значение вычисляет сама СУБД в рамках одного оператора. Вторая: блокировку строки берёт сам `UPDATE`. Вторая транзакция, пришедшая на ту же строку, встаёт в ожидание, а после коммита первой перечитывает строку и заново проверяет своё условие `WHERE` уже против нового баланса. Отдельный `SELECT ... FOR UPDATE` не нужен, это лишний round-trip, который ничего не добавляет к гарантиям. Третья: защита от овердрафта живёт в условии `WHERE`, поэтому списание, которое увело бы баланс в минус, просто не находит строку, а не откатывается постфактум. Четвёртая: в схеме стоит `CHECK (balance >= 0)` как последний рубеж. Приложение физически не может сформировать запрос, нарушающий это условие, но ошибка в будущем коде или ручной запрос к базе не должны иметь такой возможности.

Когда `UPDATE` не вернул строку, ситуация неоднозначна: либо кошелька нет, либо операция увела бы баланс в минус. Сервис делает отдельную проверку существования и различает `404` и `409`, чтобы клиенту не приходилось гадать.

Уровень изоляции — `READ COMMITTED`, то есть умолчание PostgreSQL. Для этой задачи он достаточен и предпочтителен: перепроверка условия `WHERE` после снятия блокировки, на которой всё построено, это штатное поведение именно `READ COMMITTED`. `SERIALIZABLE` дал бы те же гарантии, но ценой ошибок сериализации и обязательных повторов на ровном месте.

## Идемпотентность

Заголовок `Idempotency-Key` необязателен. Повтор запроса с тем же ключом на том же кошельке возвращает исходный результат и `"replayed": true`, деньги не двигаются второй раз.

Гарантию даёт не проверка в коде, а ограничение `UNIQUE (wallet_id, idempotency_key)` в базе. Если два одинаковых запроса идут параллельно, второй падает на уникальном индексе, и вся его транзакция откатывается целиком, вместе с изменением баланса. После этого сервис читает результат победителя гонки и отдаёт его клиенту. Проверка в коде до записи существует только как оптимизация, чтобы не трогать баланс, когда ответ уже известен, и на корректность не влияет.

Тот же ключ с другим телом запроса даёт `409`, а не повтор. Вернуть сохранённый результат означало бы ответить на вопрос, которого клиент не задавал, и молча скрыть ошибку на его стороне.

Запросы без ключа не дедуплицируются: в PostgreSQL `NULL` не равен `NULL`, поэтому уникальное ограничение их между собой не связывает.

## Поведение при ошибках и запасные пути

Отказы разделены на те, которые имеет смысл повторить, и те, которые повтор только воспроизведёт. Классификация живёт в `app/db/errors.py` и работает по SQLSTATE, а не по тексту сообщения. Транзиентными считаются deadlock `40P01`, serialization failure `40001`, срабатывание `lock_timeout` `55P03`, остановка и перезапуск сервера `57P01`, `57P02`, `57P03` и обрывы соединения семейства `08xxx`. Нарушение ограничения детерминировано и не ретраится никогда. Повтор делается целой транзакцией, до трёх попыток по умолчанию, с экспоненциальной задержкой и полным джиттером: повторять дедлок немедленно означает воспроизвести его, а повторять всем потоком одновременно означает получить лавину повторов.

Если бюджет повторов исчерпан, наружу уходит `503` с кодом `service_unavailable` и предложением повторить запрос, а не сырая ошибка драйвера. То же самое происходит с любой необработанной ошибкой SQLAlchemy: она перехватывается централизованно, подробности пишутся в лог, клиент получает `503`. Совсем необработанное исключение превращается в `500`, в теле которого нет ничего, кроме кода, общей формулировки и `request_id`, по которому сопровождение найдёт запись в логе. Ни стектрейс, ни сообщение драйвера, ни фрагмент SQL наружу не попадают ни при каких обстоятельствах.

Висящих запросов быть не может. На уровне сессии выставлены `statement_timeout`, `lock_timeout` и `idle_in_transaction_session_timeout`, поэтому запрос или ожидание блокировки гарантированно завершаются ошибкой, а не выедают пул соединений. Срабатывание `lock_timeout` при этом попадает в список транзиентных ошибок и приводит к повтору, а не к отказу. Соединения, убитые базой или прокси, обнаруживаются до выполнения запроса через `pool_pre_ping`, так что первый запрос после сетевого сбоя не падает, а переподключается.

Транзакционная граница вынесена в `UnitOfWork`, контекстный менеджер, который коммитит при успешном выходе из блока и откатывает при любом исключении. Оставить наполовину применённую транзакцию нельзя даже случайно: единственный способ работать с репозиториями проходит через этот менеджер.

Журнал операций `wallet_operations` работает как append-only и даёт запасной путь на случай расхождения: баланс всегда можно пересчитать от суммы операций и сверить с хранимым значением. В тестах это используется как проверка, что итог сходится с журналом.

Есть один случай, который решается не сервисом, а клиентом, и об этом стоит сказать прямо. Если соединение с базой обрывается ровно в момент коммита, приложение не может знать, применилась транзакция или нет; повтор в этой ситуации теоретически способен применить операцию дважды. Именно для этого и существует `Idempotency-Key`: с ним повтор упирается в уникальный индекс и возвращает исходный результат, поэтому клиентам, для которых двойное списание неприемлемо, передавать ключ обязательно. Закрывать это без участия клиента можно только генерацией ключа на стороне сервиса, что перекладывает ту же проблему на уровень выше, поэтому выбран явный и предсказуемый вариант.

## Архитектура

Код разложен по слоям с односторонними зависимостями. В `app/api/v1` лежат роутеры, схемы pydantic и зависимости, и этот слой ничего не знает о базе. В `app/services` находятся сценарии использования и бизнес-правила, и этот слой ничего не знает о HTTP, благодаря чему тестируется на подставном unit of work без базы вообще. В `app/repositories` живёт только SQL, без политики повторов и без транзакционных границ. В `app/db` находятся движок, сессии, модели, unit of work и классификация ошибок базы. В `app/domain` лежат доменные исключения и перечисления. В `app/core` собраны конфигурация, логирование, middleware и единое место, где доменные исключения превращаются в HTTP-ответы, так что добавление нового правила не требует правок в роутерах.

Миграции вынесены в отдельный сервис compose, а не выполняются на старте приложения. При нескольких репликах старт на каждой означал бы гонку за одну и ту же миграцию; отдельный шаг, завершающийся до запуска API, снимает вопрос. В CI миграции дополнительно проверяются циклом upgrade, downgrade до базы и снова upgrade, чтобы откат не оказался фикцией.

## Схема данных

Таблица `wallets` содержит `id` типа UUID с `gen_random_uuid()` по умолчанию, `balance` типа `NUMERIC(20,2)` с ограничением `CHECK (balance >= 0)`, а также `created_at` и `updated_at` типа `TIMESTAMPTZ`. Значение `updated_at` поддерживается триггером в базе, а не только средствами ORM, поэтому остаётся честным и для записей в обход приложения.

Таблица `wallet_operations` хранит `wallet_id`, `operation_type`, `amount`, `balance_after`, необязательный `idempotency_key` и `created_at`. На ней стоят ограничения `CHECK (amount > 0)` и `CHECK (balance_after >= 0)`, уникальное ограничение по паре `wallet_id` и `idempotency_key`, внешний ключ на кошелёк с каскадным удалением и индекс по паре `wallet_id` и `created_at` для выборок истории.

Деньги везде представлены типом `Decimal`, в базе это `NUMERIC(20,2)`. `float` не используется нигде: `0.1 + 0.2 != 0.3` неприемлемо для денежных величин. Суммы нормализуются до двух знаков на границе API, поэтому сервис и база всегда видят одинаковый масштаб. Целые копейки были бы столь же корректны, но `NUMERIC` выбран потому, что арифметика остаётся точной внутри базы, суммы в журнале читаются человеком без пересчёта, а смена масштаба, например на четыре знака, сводится к правке типа колонки, а не к ревизии всего кода.

## Тесты

Всего 64 теста, покрытие 92 процента. Модульные тесты в `tests/unit` проверяют бизнес-правила, идемпотентность и политику повторов на подставном unit of work, без базы. Интеграционные тесты в `tests/integration/test_wallet_api.py` проходят по всем эндпоинтам и проверяют коды ответов, валидацию, формат ошибок, сквозной `request_id`, идемпотентность и точность дробных сумм.

Отдельного внимания заслуживает `tests/integration/test_concurrency.py`, потому что именно он проверяет главное требование задания. Сто параллельных списаний при балансе, которого хватает ровно на десять, должны дать десять успехов, девяносто отказов и итоговый ноль; дополнительно проверяется, что все записанные значения `balance_after` различны, поскольку совпадение двух из них было бы прямой подписью потерянного обновления. Тот же сценарий повторяется через HTTP. Перемешанные пополнения и списания проверяются на сходимость итогового баланса с суммой журнала. Двадцать одновременных запросов с одним ключом идемпотентности должны сдвинуть деньги один раз и вернуть один и тот же идентификатор операции во всех ответах. Наконец, проверяется, что операции над разными кошельками не мешают друг другу.

Интеграционные тесты работают против настоящего PostgreSQL, а не против SQLite или моков, потому что проверяются гарантии, которые даёт именно блокировка строк в PostgreSQL, и никакой заменитель здесь ничего не докажет.

## Конфигурация

Все параметры задаются переменными окружения, полный список с комментариями лежит в `.env.example`. Подключение к базе описывается переменными `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`. Режим работы задаётся переменной `ENVIRONMENT` со значениями local, test, staging или production, уровень логирования переменной `LOG_LEVEL`. Флаг `DOCS_ENABLED` выключает Swagger и схему OpenAPI для публичного развёртывания. Поведение под нагрузкой настраивается переменными `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_STATEMENT_TIMEOUT_MS`, `DB_LOCK_TIMEOUT_MS` и `DB_RETRY_ATTEMPTS`. Верхняя граница одной операции задаётся переменной `MAX_OPERATION_AMOUNT`.

Настройки валидируются pydantic-settings при старте, поэтому опечатка в значении приводит к отказу запуска, а не к странному поведению под нагрузкой.

## Безопасность

Все входящие модели объявлены с `extra="forbid"`, то есть неизвестное поле в теле запроса это ошибка клиента, а не молча проигнорированные данные. Суммы ограничены сверху и снизу, ограничены двумя знаками после запятой, значения `NaN` и `Infinity` отбрасываются явно, UUID валидируется на уровне пути. Наружу не уходит ни стектрейсов, ни сообщений драйвера. Логи структурированные, в формате JSON, со сквозным идентификатором запроса; клиентский `X-Request-ID` принимается, но обрезается по длине и санитизируется, поскольку попадает в лог, а неограниченный пользовательский ввод там не нужен. Образ собирается многоэтапно, в рантайме нет ни компилятора, ни пакетного менеджера, процесс работает от непривилегированного пользователя. Секреты передаются только через окружение, в репозитории лежит `.env.example`, реальный `.env` в `.gitignore`. Порт базы наружу не публикуется, она доступна только внутри сети compose.

## Чего намеренно нет

Аутентификации в сервисе нет. В задании её нет, а добавлять её по своему усмотрению значит принять за заказчика решение о модели угроз. В реальной системе это был бы JWT или mTLS от API-gateway, а сам сервис оставался бы внутренним; точка подключения очевидна и находится в зависимостях роутера в `app/api/v1/deps.py`.

Ограничения частоты запросов в сервисе тоже нет, и по той же причине: его место на ingress или API-gateway. Внутри приложения лимит считался бы отдельно в каждом воркере и в каждой реплике, то есть не работал бы как лимит.

Списка операций по кошельку нет, хотя журнал для него уже есть: эндпоинт в задании не требуется, а добавлять публичный API с пагинацией и фильтрами без требований к нему означает угадывать.

## Качество кода

Линтер ruff настроен строго и включает pycodestyle, pyflakes, isort, pep8-naming, pyupgrade, bugbear, flake8-bandit для безопасности, flake8-annotations и правила pylint. Проверка типов выполняется mypy в режиме strict. Настроен pre-commit. CI на GitHub Actions состоит из трёх задач: линтеры и типы, тесты против PostgreSQL с предварительной проверкой обратимости миграций, и сборка образа. Предупреждений при прогоне тестов нет ни одного.

## Воспроизводимость сборки

В `pyproject.toml` зависимости заданы нижними границами, то есть описывают совместимость, а не конкретный набор версий. Точные версии зафиксированы в `uv.lock`, который лежит в репозитории: там записаны разрешённое дерево целиком и хеши артефактов. Благодаря этому CI, образ и локальная машина ставят одно и то же, а выход новой версии транзитивной зависимости не ломает сборку задним числом.

Лок не просто лежит в репозитории, а действительно используется. Установка и в CI, и в Docker, и локально выполняется командой `uv sync --frozen`: флаг запрещает перерешать зависимости, поэтому расхождение между `uv.lock` и `pyproject.toml` приводит к падению сборки, а не к молчаливому обновлению. В CI перед установкой отдельным шагом выполняется `uv lock --check`, который ловит ровно эту рассинхронизацию, а все последующие шаги работают из собранного по локу окружения.

Обновление зависимостей — осознанное действие: `make lock` (то есть `uv lock`) перерешает дерево и меняет `uv.lock`, после чего изменение видно в диффе и проходит ревью, как любой другой код.

## Разработка без Docker

Нужен работающий PostgreSQL.

```bash
make install          # uv sync --frozen --extra dev, окружение в .venv
source .venv/bin/activate
export POSTGRES_HOST=localhost POSTGRES_USER=wallet POSTGRES_PASSWORD=wallet POSTGRES_DB=wallet
alembic upgrade head
uvicorn app.main:app --reload
```

Проверки запускаются через `make lint`, автоисправления через `make format`, обновление зависимостей через `make lock`.
