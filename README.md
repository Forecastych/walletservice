# Wallet Service

Асинхронный REST API для работы с кошельками пользователей.
FastAPI + PostgreSQL, полностью в Docker, запускается одной командой.

Ключевое свойство: **параллельные операции над одним кошельком обрабатываются
корректно** — без потерянных обновлений и без ухода баланса в минус.

---

## Быстрый старт

```bash
cp .env.example .env      # необязательно: значения по умолчанию рабочие
docker compose up --build
```

Поднимутся три сервиса: база, разовый прогон миграций и API. Приложение
дожидается и готовности базы, и успешного завершения миграций, поэтому под
трафик никогда не попадает наполовину применённая схема.

* API — http://localhost:8000
* Swagger — http://localhost:8000/docs

Тесты:

```bash
docker compose --profile test run --rm tests
```

Всё то же самое есть в `Makefile`: `make up`, `make test`, `make lint`, `make clean`.

## API

### Создать кошелёк

```http
POST /api/v1/wallets
Content-Type: application/json

{ "initial_balance": "1000.00" }     # тело необязательно, по умолчанию 0
```

`201 Created` → `{"id": "...", "balance": "1000.00"}`

В исходном ТЗ этого эндпоинта нет, но без него кошелёк нечем создать, поэтому
он добавлен.

### Получить баланс

```http
GET /api/v1/wallets/{WALLET_UUID}
```

`200 OK` → `{"id": "...", "balance": "1000.00"}`

### Изменить баланс

```http
POST /api/v1/wallets/{WALLET_UUID}/operation
Content-Type: application/json
Idempotency-Key: order-4711          # необязательный заголовок

{ "operation_type": "DEPOSIT", "amount": 1000 }
```

`200 OK` → `{"wallet_id": "...", "operation_id": "...", "operation_type": "DEPOSIT", "amount": "1000.00", "balance": "2000.00", "replayed": false}`

### Коды ответов

| Код | Когда |
|-----|-------|
| `200` | Операция применена или распознана как повтор |
| `201` | Кошелёк создан |
| `404` | Кошелька с таким UUID нет |
| `409` | Недостаточно средств, либо ключ идемпотентности переиспользован с другим телом |
| `422` | Невалидный запрос (сумма ≤ 0, больше двух знаков после запятой, неизвестный `operation_type`, битый UUID, лишние поля) |
| `503` | База недоступна или транзакция не прошла после всех повторов |

Все ошибки имеют один формат:

```json
{
  "code": "insufficient_funds",
  "message": "Wallet ... has insufficient funds for a withdrawal of 500.00",
  "request_id": "0f6c...",
  "details": null
}
```

`code` стабилен и предназначен для машинной обработки, `request_id` совпадает с
заголовком `X-Request-ID` и с полем в логах.

### Health-эндпоинты

* `GET /health/live` — процесс жив. Базу намеренно не трогает: сбой БД не должен
  приводить к тому, что оркестратор убьёт здоровый процесс.
* `GET /health/ready` — готов принимать трафик, то есть база отвечает.

## Конкурентность

Это основная часть задачи, поэтому подробно.

Изменение баланса — **один атомарный SQL-запрос**:

```sql
UPDATE wallets
   SET balance = balance + :delta
 WHERE id = :wallet_id
   AND balance + :delta >= 0
RETURNING balance;
```

Почему именно так:

1. **Нет окна read-modify-write.** Классическая ошибка — прочитать баланс в
   Python, посчитать новый и записать обратно. Между чтением и записью успевает
   вклиниться другая транзакция, и одно из списаний теряется. Здесь чтения в
   приложении нет вообще: текущее значение и новое вычисляет сама СУБД в рамках
   одного оператора.
2. **Блокировку берёт сам `UPDATE`.** Вторая транзакция, пришедшая на ту же
   строку, встаёт в ожидание, а после коммита первой **перечитывает строку и
   заново проверяет свой `WHERE`** — уже против нового баланса. Отдельный
   `SELECT ... FOR UPDATE` не нужен: это лишний round-trip, который ничего не
   добавляет.
3. **Защита от овердрафта живёт в `WHERE`.** Списание, которое увело бы баланс в
   минус, просто не находит строку, а не откатывается постфактум.
4. **`CHECK (balance >= 0)` в схеме** — последний рубеж. Приложение не может
   сформировать запрос, нарушающий это условие, но ошибка в коде или ручной
   запрос не должны иметь такой возможности.

`UPDATE` не вернул строку — сервис отдельно проверяет существование кошелька и
различает `404` и `409`, чтобы клиент не гадал.

### Уровень изоляции

Используется `READ COMMITTED` (по умолчанию в PostgreSQL). Для этой задачи он
достаточен и предпочтителен: описанная выше перепроверка `WHERE` после снятия
блокировки — штатное поведение именно `READ COMMITTED`. `SERIALIZABLE` дал бы те
же гарантии, но ценой ошибок сериализации и обязательных повторов на ровном
месте.

### Что ещё сделано ради корректности под нагрузкой

* **Retry с классификацией ошибок.** Повторяются только транзиентные сбои
  (deadlock `40P01`, serialization failure `40001`, lock timeout `55P03`, обрывы
  соединения). Нарушение ограничения детерминировано — повтор его воспроизведёт,
  поэтому оно не ретраится.
* **`statement_timeout` и `lock_timeout`** на уровне сессии: запрос или ожидание
  блокировки не могут висеть вечно и выесть весь пул соединений.
* **`pool_pre_ping`** — соединение, убитое базой или прокси, обнаруживается до
  выполнения запроса.
* **Журнал операций** (`wallet_operations`) — append-only. Баланс всегда можно
  пересчитать и сверить; в тестах это используется для проверки, что итог
  сходится с суммой операций.

### Идемпотентность

Необязательный заголовок `Idempotency-Key`. Повтор запроса с тем же ключом
возвращает исходный результат и `"replayed": true` — деньги не двигаются второй
раз.

Гарантию даёт не проверка в коде, а ограничение `UNIQUE (wallet_id,
idempotency_key)`. Если два одинаковых запроса идут параллельно, второй падает на
уникальном индексе, и **вся его транзакция откатывается целиком, вместе с
изменением баланса**. После этого сервис читает результат победителя и отдаёт
его. Проверка в коде до записи — только оптимизация, чтобы не трогать баланс,
когда ответ уже известен.

Тот же ключ с другим телом запроса — это `409`, а не повтор: вернуть
сохранённый результат означало бы ответить на вопрос, которого клиент не задавал.

Запросы без ключа не дедуплицируются: в PostgreSQL `NULL` не равен `NULL`,
поэтому уникальное ограничение их не затрагивает.

## Архитектура

```
app/
├── api/v1/          роутеры, pydantic-схемы, зависимости
├── core/            конфиг, логирование, обработчики ошибок, middleware
├── db/              engine, сессии, модели, unit of work, классификация ошибок БД
├── domain/          доменные исключения и enum'ы
├── repositories/    только SQL
└── services/        бизнес-логика (use cases)
migrations/          Alembic
tests/
├── unit/            сервис на фейковом UoW, без базы
└── integration/     API и конкурентность на настоящем PostgreSQL
```

Слои разделены по направлению зависимостей: роутер ничего не знает о базе,
сервис — о HTTP. Доменные исключения превращаются в HTTP-ответы в одном месте
(`app/core/errors.py`), поэтому добавление нового правила не требует правок в
роутерах.

Транзакционная граница — `UnitOfWork`: контекстный менеджер, который коммитит
при успешном выходе и откатывает при любом исключении. Оставить наполовину
применённую транзакцию физически нельзя.

### Схема данных

**`wallets`**

| Поле | Тип | |
|------|-----|---|
| `id` | `UUID` | PK, `gen_random_uuid()` |
| `balance` | `NUMERIC(20,2)` | `CHECK (balance >= 0)` |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | `updated_at` поддерживается триггером |

**`wallet_operations`** — журнал: `wallet_id`, `operation_type`, `amount`,
`balance_after`, `idempotency_key`, `created_at`, плюс
`UNIQUE (wallet_id, idempotency_key)` и индекс `(wallet_id, created_at)`.

### Деньги

Везде `Decimal`, в базе `NUMERIC(20,2)`. `float` не используется нигде: `0.1 +
0.2 != 0.3` — неприемлемо для денег. Суммы нормализуются до двух знаков на
границе API, поэтому сервис и база всегда видят одинаковый масштаб.

## Безопасность

* **Валидация.** `extra="forbid"` на всех входящих моделях, строгие границы для
  сумм (> 0, ≤ 10⁹, максимум два знака), UUID валидируется на уровне пути.
  `NaN` и `Infinity` отбрасываются явно.
* **Ошибки наружу.** Ни стектрейсов, ни сообщений драйвера. Непредвиденное
  исключение превращается в `500` с одним лишь `request_id`; подробности уходят
  в лог.
* **Логи.** Структурированный JSON, сквозной `request_id`. Клиентский
  `X-Request-ID` принимается, но обрезается по длине и санитизируется — он
  попадает в логи, и неограниченный ввод там не нужен.
* **Контейнер.** Multi-stage сборка, в рантайме нет ни компилятора, ни пакетного
  менеджера. Процесс работает от непривилегированного пользователя `app`
  (uid 1001).
* **Секреты.** Только через окружение. В репозитории лежит `.env.example`, сам
  `.env` в `.gitignore`. Настройки не имеют пригодных дефолтов для пароля.
* **Сеть.** Порт базы наружу не публикуется — она доступна только внутри сети
  compose.
* **Документация.** Swagger и OpenAPI выключаются флагом `DOCS_ENABLED=false`.

### Чего намеренно нет

**Аутентификации.** В ТЗ её нет, и добавлять её «на всякий случай» — значит
принимать за заказчика решение о модели угроз. В реальном проекте это был бы
JWT или mTLS от API-gateway, а сам сервис оставался бы внутренним. Точка
подключения очевидна: зависимость на уровне роутера в `app/api/v1/deps.py`.

**Rate limiting.** Место ему — на ingress/API-gateway, а не в самом сервисе:
иначе лимит считается отдельно в каждом воркере и в каждой реплике.

## Тесты

```bash
docker compose --profile test run --rm tests
```

* **`tests/unit/`** — сервис на фейковом unit of work. Проверяются правила и
  политика повторов, без базы.
* **`tests/integration/test_wallet_api.py`** — все эндпоинты, коды ответов,
  валидация, идемпотентность, точность дробных сумм.
* **`tests/integration/test_concurrency.py`** — главное:
  * 100 параллельных списаний при балансе, которого хватает на 10: ровно 10
    успешных, 90 отказов, итог `0.00`, и все `balance_after` различны —
    совпадение означало бы потерянное обновление;
  * то же через HTTP;
  * перемешанные пополнения и списания: итоговый баланс сходится с суммой
    журнала;
  * 20 одновременных запросов с одним `Idempotency-Key`: деньги двигаются один
    раз, все ответы описывают одну и ту же операцию;
  * операции над разными кошельками не влияют друг на друга.

Интеграционные тесты работают против настоящего PostgreSQL, а не против SQLite
или моков: проверяются гарантии, которые даёт именно блокировка строк в
PostgreSQL, и заменитель тут ничего не докажет.

## Разработка без Docker

Нужен работающий PostgreSQL.

```bash
make install                 # uv venv + зависимости
source .venv/bin/activate
export POSTGRES_HOST=localhost POSTGRES_USER=wallet \
       POSTGRES_PASSWORD=wallet POSTGRES_DB=wallet
alembic upgrade head
uvicorn app.main:app --reload
```

Линтеры и типы:

```bash
make lint      # ruff check + ruff format --check + mypy
make format    # автоисправления
```

`ruff` настроен строго: pycodestyle, pyflakes, isort, pep8-naming, bugbear,
flake8-bandit (безопасность), flake8-annotations, pylint. `mypy` — в режиме
`strict`. Есть конфиг `pre-commit`.

## Замечания по решениям

**Почему `NUMERIC`, а не целые копейки.** Оба варианта корректны. `NUMERIC(20,2)`
выбран потому, что арифметика остаётся точной внутри базы, суммы в журнале
читаются человеком без пересчёта, а смена масштаба (скажем, на четыре знака для
валют вроде BHD) — это правка типа колонки, а не ревизия всей кодовой базы.

**Почему миграции отдельным сервисом, а не на старте приложения.** При нескольких
репликах старт на каждой означает гонку за одну и ту же миграцию. Отдельный шаг,
завершающийся до запуска API, снимает вопрос.

**Почему журнал операций, хотя ТЗ его не требует.** Без него баланс — число без
истории: нельзя ни сверить, ни расследовать расхождение. Плюс он же даёт
идемпотентность, не требуя отдельного хранилища.
